# create-pr(PR本文を構造化して投稿する)

## 1. 差分と経緯を集める
- `git diff master...HEAD` で変更の全体を把握する
- 対応するタスク文書(docs/tasks/projects/phaseN/task.md 等)・
  チェックリスト(docs/tasks/projects/phaseN/plans/)と、`/code-review`の
  結果を読む

## 2. 本文を下書きする

次の見出しで、レビューアーが上から読めば理解できる順に書く

- 課題: 何を解決するPRか(背景と、対応するタスク文書・サイクル)
- 解決策: どう変えたか。設計判断とトレードオフを1〜2行で
- テスト: 追加・変更したテストと、手元での実行結果(cargo test / pnpm typecheck等)
- レビュー観点: とくに見てほしい箇所、影響範囲、未対応事項

下書きをそのまま提示し、投稿前に人間の承認を得る(専用の保存先は設けない。
docs/tasks/README.md「現役文書から実行系タスクへ直接リンクしない」規約に
沿い、下書き自体をdocs/配下へ永続化しない)。

## 3. 投稿する

承認後、`gh pr create` で本文を渡して作成する。CIと`/code-review`が回るので、
その結果が出てから人間のレビューへ回す。masterへのマージは人間の判断を仰ぐ
(CLAUDE.md「やらないこと」)。
