# 単体/E2Eの切り分けと骨抜き禁止

## 種別と実行コマンド

種別|ツール|置き場所|実行|何を守るか
--|--|--|--|--|
単体|Vitest|`tests/unit`(srcの構造を再現)|`npx vitest run`|ロジックの境界値・異常系
E2E|Playwright|`tests/e2d`|`npx playwright test`|主要フロー・認可・状態遷移

- 単体の置き場所はsrcのパスを再現する(例: `src/lib/tax.ts` -> `tests/unit/lib/tax.test.ts`)
- E2Eは実行前にシードデータの投入とアプリ起動が要る(後述)

## 単体とE2Eの切り分け

E2Eで検証する:
- ユーザーフローの完走(ログイン->操作->結果の確認)
- 認証・認可(他人のデータが見えない・権限で表示が変わる)
- 複数画面やAPIをまたぐ総合動作、状態遷移(ローディング->成功/エラー)
- 実APIとの通信を含むフロー(モックしない)

単体で検証する:
- 純粋な計算・整形・バリデーション（外部I/Oなし）
- E2Eでは網羅しにくい細かい分岐

中間(統合テスト)に落とす
- DBをまたぐ制御フロー、APIルート・Server Actionの薄い制御
- E2Eにするとモックが増えすぎて実装詳細に張り付くケース

## E2Eのシードデータ

E2Eは固定のシードデータを入れたデータベースに対して走らせる。ログインできる。
テストユーザと権限の違いを確かめるための組織・プランをあらかじめ用意しておく。

- シードは１つの定義ファイル(例: `tests/e2e/seed-data.md`と`db/seed.sql`)に集約し、テスト内で独自のマジック値を作らない。
- 最低限用意する: プラン/ロール別のログインユーザ(管理者・一般など固定メール＋固定ID)、権限確認用の「別の組織のデータ」
- 実行の流れ: `npm run db:seed` (シード投入) -> アプリ起動 -> `npx playwright test`
- 読み取り専用のテストは既存シードを使う。変更を伴うテストは専用データをfixturesで作り、後始末する (共有シードを書き換えると並列実行で他のテストが壊れる)

## 骨抜き禁止

// ✖ 何も守っていない
expect(result).toBeDefined();
// ✖ 常時成功モック（本物が壊れても通る）
vi.mock('./calcTax',()=> ({ calcTax: ()=> 1000}));
// ✖ 条件好きスキップ（環境がないと黙って成功扱い）
if (!process.env.API_KEY) return;

// ✅ 期待値を固定してassertする。協会の内側を書く
expect(calcTax(10000)).toBe(1000);
expect(calcTax(0)).toBe(0);


- E2Dでアプリ内部のAPI応答をモックしない（結合を確かめるのがE2Eの仕事）
- `.only` / `.skip`を残したままコミットしない
- 新規テストは先にRed(失敗)を確認してから実装する

## テストの独立性 (並列実行対応)

- 各テストが自分専用のデータを作り、終了時に片づける
- 他のテストが作ったデータ・実行順序に依存しない
- `waitForTimeout` で待たず、 `expect(...).toPass()` やロケータの自動待機を使う
-  セレクタは role/labe/testid を優先し、CSSクラスに依存しない
