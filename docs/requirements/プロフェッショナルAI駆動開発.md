# 概要
書籍プロフェッショナルAI駆動開発を読んだ。
そこのエッセンスを本プロジェクトにも取り入れたい。
書籍に記載のチェックリストを転記し、本プロジェクトの現在の状況認識を整理する

# 前提
ここでは開発をY=F(X)という式でとらえる。
この文脈の用語を定義する。今回はAI駆動開発の文脈で使用する。

変数|論理名|従来開発|AI駆動開発
--|--|--|--
X|インプット|仕様書+開発者が暗黙に補う文脈|AIに明示的に与えた情報がすべて
F|変換|人間の頭脳。責任をもって質問し補完する|LLM。与えられた範囲で確率的に変換する。
Y|アウトプット|書いた本人が意図を説明できるコード|提出者(AI)は意図の責任を負わないコード

# 毎タスクのチェックリスト(第７章)
- [ ] プランを書いた（８項目。AIに逆質問させてから）
- [ ] プランをレビューにかけた（観点別・P0は実装前に反映）
- [ ] テストケース一覧に人間がビジネスの目で介入した（機械的な網羅だけで確定しない）
- [ ] 実装はプランを渡すだけにした（口頭の追加要件を足さない）
- [ ] Redを確認してからGreenにした（最初から通るテストを疑う）
- [ ] 実装レビューを別セッションで走らせた（P0/P1ゼロまで。往復は１～４回で打ち切り）
- [ ] マージ前に決めたテスト一式を回した

# 週次・月次のチェックリスト(第７章)
- [ ] 本番までのX:デプロイ設定とログ基盤に接続したか。「コードは完璧なのに動かない」の原因が式の外に残っていないか
- [ ] テストの信頼性：スキップ条件と不要なモックをレビューで潰したか。ごまかしの新パターンはルールとスキルに書き足したか
- [ ] 劣化の返済：無限ループが頻発しはじめたらコードベースの劣化を疑う。定期リファクタリングを止めていないか
- [ ] ルールの鮮度：レビューで同じ指摘が繰り返されたら、ルールファイルへ昇格させたか

# 品質が揺れた時： X->Y->F の順に疑う (第2～6章)
- [ ] X: コンテキストは劣化していないか（鮮度・必要十分性・一貫性。長すぎるセッション・古い文書・矛盾するルール）
- [ ] Y: テストは信用できるか（骨抜き・スキップ・網羅の穴）。テストがGreenでも守備範囲の外ではないか
- [ ] 最後にモデル設定を疑う（タスクに正解はあるか→安定型/探索型。複雑さ→賢さ。並列に値する難所か）
