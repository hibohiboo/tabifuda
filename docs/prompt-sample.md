
# 概要
開発フローのステップで使う依頼文サンプル。【】の穴を埋めて使う。
実際のスキル名・置き場所はこのリポジトリの規約(CLAUDE.md・
docs/agent-operations.md・docs/tasks/README.md)に合わせてある。

# 1. チェックリストの作成(インタビュー式)

phase-cycleスキル「2. 実装」の「着手前にチェックリスト化する」の対話版。

```
【サイクル名】(例: Phase1 C2)に着手したい。概要: 【2〜3行で】
参考: docs/tasks/projects/【phaseN】/task.md の該当サイクルと
docs/design/【関連する規範文書】

まず実装に入らず、チェックリストを書くために必要な質問を私にすること。
技術面・エッジケース・トレードオフについて、答えにくい質問ほど価値がある。
質問が尽きたら、チェックリストを
docs/tasks/projects/【phaseN】/plans/【cycle】-checklist.mdに書き出すこと。
実装順には、どのタスクをどのモデル・サブエージェントに任せるかの
割り当てまで書くこと(docs/agent-operations.md「タスク種別ごとの割り当て」参照)。
```

# 2. チェックリストのAIレビュー(観点別)
実装セッションとは別のセッションで

```
docs/tasks/projects/【phaseN】/plans/【checklist】.mdをレビューすること。
私は書いた本人ではない前提で読む。
観点: [設計整合性/セキュリティ/テスト網羅 から1つ]
判定の基準: [docs/design/の該当規範文書 または .claude/rules/の該当ルール]
指摘はP0(実装前に必ず直す)/P1(推奨)/P2(軽微)に分類し、
チェックリストのどの記述が・どの基準と・なぜズレるのかを1件ずつ示すこと。
```

# 3. テスト網羅のレビュー

```
docs/tasks/projects/【phaseN】/plans/【checklist】.md の「テスト」項目だけを
レビューすること。docs/design/test-strategy.mdの受理/拒否対の方針と
突き合わせ、
[1] Commandに対応する正常系・拒否系のテストが欠けていないか
[2] 境界値の両側・異常系が入っているか
[3] スコープ外と決めた将来要望がテストに紛れていないか
を確認し、足りないテストケースを提案すること。
```

# 4. 実装
レビュー済チェックリストを渡すだけにする。

```
docs/tasks/projects/【phaseN】/plans/【checklist】.md の実装順に従って実装すること。
割り当てどおり、[調査/ユーティリティ]はサブエージェントに任せてよい。
チェックリストにない変更が必要になったら、実装せずに立ち止まって報告すること
(docs/agent-operations.md「ソースコード変更はタスク発行が前提」)。
```

# 5. テストの実装を全通過
tddスキルのRed/Green/Refactorをそのまま使う。

```
チェックリストの「テスト」項目をテストコードに落とすこと。/tdd で進める。
各テストは先に実行して失敗(Red)を確認してから実装を直す。
最初から通ってしまったテストは、実装済みかassertが弱いかを判定して報告する。
最後に[cargo test --workspace 等、変更範囲に応じた検証コマンド]を実行し、
全通過の出力を見せること。
```

# 6. 実装のレビュー(観点別並列)

```
実装が終わった。次のサブエージェントを並列で実行し、
報告をP0からP2に整理して返すこと。
- design-reviewer: チェックリストとの整合
- edge-case-reviewer: 異常系と境界値の抜け
セキュリティ観点は /code-review(cross-cutting.mdの権限・UGC・削除方針を
基準にする)を別途実行する。
```

# 7. 人間のレビュー(AIへの壁打ち)
AIに判定させない唯一の型。
厚みは機能の重要度で考え、影響の小さい機能なら省略してよい。

```
実装した【機能名】について、レビューする私に説明すること。判定はしなくてよい。
1. 変更の要点を、データの流れがわかる粒度で説明する。
2. 設計判断を3つまで挙げ、それぞれ採らなかった選択肢と併記する。
3. 各判断の根拠が、docs/tasks/projects/【phaseN】/plans/【checklist】.md の
   どこかにあるかを引用して示す。書いていないものは「実装時の判断」と明示
4. 壊れた時に影響が大きい箇所を、理由とともに挙げる。
   判断できないものは推測で進めず「不明」と答えること。
```

# 8. テスト駆動リファクタリング
機能単位ではなく定期実行する。安全網の確認から始めさせるのが型。

```
【対象ディレクトリ】をリファクタリングすること。機能の変更はしない。
先に対象のテストを実行して全部Greenであることを確認し、
そこから1変更ごとにテストを回して、Greenを保ったまま進めること。
観点: 1ファイル1責務に反する肥大したファイルの分割(CLAUDE.md最重要ルール5)、
重複した処理の集約、.claude/rules/【該当パスのルール】との乖離の解消。
テストが赤くなったら、その変更を巻き戻して報告すること。
```
