# UI/ビジュアルデザイン方針

対象: apps/web(P3 C2以降)。本文書は**見た目・演出のトーン&マナー**を扱う。
機能的な表示・操作規約(何を出す/出さないか)は
[client-conventions.md](client-conventions.md) が正であり、本文書とは役割が異なる。

**位置づけ: 非規範の方針メモ**。domain-model.md/client-conventions.mdのような
「変えるときは先に文書を直す」規範ではなく、C2以降のUI実装で迷ったときに
立ち返る指針集。実装を進める中で方針が変わったら本文書を更新する。

## 基本方針

1. **モバイルファースト**。まずスマホ縦持ちで成立するレイアウトを作り、
   PC版はその拡張として作る(逆(PCを作ってから縮小対応)はしない)。
2. **視認性・操作性を最優先**。演出やビジュアルの作り込みより、
   「読める」「押しやすい」「今何が起きたか分かる」を優先する。
3. **ダークモード固定**。ライト/ダークの切替機能は用意しない
   (将来要望が出たら future-requirements.md に送る)。
4. **PC版はカードワースの雰囲気を意識するが、模倣が目的ではない**。
   シナリオデッキのように原作CardWirthにない概念は、別のカード系UIから
   良い部分を取り入れてよい。

## 対応優先度

モバイルを最優先で作り込み、PC版はレイアウトが崩れない範囲に留める
(PC版の作り込みは本フェーズのスコープ外。将来要望として扱う)。

## 演出の強さ

**視認性・操作性優先でシンプルにする**。モバマス/進撃のバハムートのような
イラストメインの演出強化アプリは参考にしない方針とする
(それらはイラスト前提の演出であり、本プロジェクトはテキストメインのカードが
主役のため、演出よりも情報の読みやすさを優先する)。

- カード出現・遷移に最小限のアニメーションは可(状態変化の把握を助ける範囲)
- 装飾目的だけのエフェクト・演出は入れない

## カードのビジュアル方針(P6で規範化、2026-08-12)

経緯: P3.5完了後の見直し
([tasks/plans/post-p3.5-replanning-decisions.md](../tasks/plans/post-p3.5-replanning-decisions.md)
Q2)で、「わくわくしない」主因を(c)演出の薄さと判定した際の決定事項。
**「演出」という語だが、決定した打ち手はモーション演出の追加ではなく
カードのビジュアル仕様である**(上記「演出の強さ」の方針とは矛盾しない)。

- **文章メインでの差別化**: CardWirthとの差別化はイラスト量では張り合わない。
  テキスト情報を主役に据える
- **カード種類に応じた既定アイコン**: カードを1枚ずつ描き起こすのではなく、
  `CardKind` ごとの既定アイコンを用意する方式にする
  - **調達方法(C1着手前決定、2026-08-12)**: 自作SVG。アイコンフォント・
    ライブラリは導入せず、`packages/ui` 内に `CardKind` 種別分のSVGを
    直接用意する
- **カードは2サイズ**:
  - 小: タイトル+アイコンのみ。CardWirthの74x94相当の画像が収まるサイズ
  - 大: スマホでも読みやすい、詳細情報を含むサイズ
- **形状**: 白銀比(1:√2)の縦長

実装は [tasks/projects/phase6/task.md](../tasks/projects/phase6/task.md)。
依頼(シナリオ)選択を張り紙カードから選ぶ案は、シナリオ選択機能自体が
未実装のため P6 のスコープ外(future-requirements.md へ送る)。

## 画面ごとのUI方向性

### 手札選択(プレイ中の操作画面)

デジタルTCG(Hearthstone/Shadowverse等)の手札UIを参考にする。
下部に手札を並べ、選んで場に出す操作感を踏襲する。

**操作フロー(P6 C2決定、2026-09-11)**: 手札は小サイズCardの一覧で並べる。
タップすると大サイズCard(`CardLarge`)をモーダル/オーバーレイで画面中央に
表示し、内容(名前・本文・種類。Dialogueのみ自由入力欄も表示)を確認して
から「出す」で確定する。**全種類統一でこの2段階を踏む**(即時使用可能な
種別だけワンタップ即時使用にする例外は設けない。誤タップでの誤使用を防ぐ
ため)。

### 冒険記(セッションのイベントログ)

タイムライン+カタログのリスト表示を参考にする。CardPlayedやScenarioPatched等の
イベントを時系列カードとして並べる仕様(task.md C3)自体は
[domain-model.md](domain-model.md)・[client-conventions.md](client-conventions.md)の規範に従うが、
**視覚表現の初期案**として以下を採用する:

- 俯瞰時は「フェーズ」を1つの山(束)として表示する
- 山を開くと、その中のイベント(カード)がリストとして展開される
- 「山(束) → 開くとカードのリスト」という入れ子構造を、フェーズ単位・
  シーン単位など複数の階層で繰り返す(**山札とカードのフラクタルな構造**)

これは初期案であり、C3実装時に実データ量(イベント数)を見て調整してよい。

## 配色・フォント・実装手段(P6 C2決定、2026-09-11)

- **配色**: apps/webの既存ダークモード配色(背景`#14141a`/カード背景`#1c1c24`・
  文字`#e8e6df`)を基調として維持する。加えて**カード種別(CardKind)ごとに
  縁取り色を分ける**(視認性優先の方針上、イラストではなく色で種別を
  素早く判別できるようにする。文章メインの差別化方針とは矛盾しない):
  - Action(行動): `#d97a3d`(オレンジ)
  - Scenario(進行): `#4d8fc4`(青)
  - Dialogue(対話): `#5aab6b`(緑)
  - Proposal(提案): `#a675d1`(紫)
  - Item(道具): `#c2a23a`(琥珀)
  - Marker(印): `#7d7d84`(グレー。手札には出ないがカタログ・GM裁定パネル用)
- **フォント**: 追加導入せず、既存の`system-ui, sans-serif`スタックを継続する
  (Webフォント導入は依存・読み込みコストが増えるため見送り)
- **UIコンポーネントライブラリ**: 不採用。C1と同じく`packages/ui`内の
  自作CSS(`tf-`プレフィックス)を継続する
- **アニメーション実装手段**: ライブラリ導入せずCSS Transitionのみ。
  「演出の強さ」方針どおり、状態変化の把握を助ける最小限(カード展開の
  モーダル表示のフェード程度)に留める

実装は [tasks/projects/phase6/plans/c2-checklist.md](../tasks/projects/phase6/plans/c2-checklist.md)。
