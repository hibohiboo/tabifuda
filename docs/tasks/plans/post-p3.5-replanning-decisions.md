## 現状分析

### 1. 計画構造: 残フェーズがインフラのみで、「遊びの価値」を増やす工程が無い

[roadmap.md](../../roadmap.md) の残フェーズは
P4(バックエンド: Hono+Drizzle+Neon)と P5(AWSデプロイ)。
どちらも配布・マルチプレイの**土台**であり、プレイ体験そのものを
豊かにする工程ではない。

一方、体験を豊かにしうる要望はすべて
[future-requirements.md](../../requirements/future-requirements.md) に
「今は作らない(壊さないよう意識するだけ)」の棚として据え置かれている:

- §2 キャンペーンシナリオ(攻略履歴の引き継ぎ)
- §3 作者定義の報酬(`rewards`)・キャラメイク用ポイント
- §4 カードのタグシステム(`#炎`で蜘蛛の巣を焼く等、CardWirthらしい発見)
- §5 条件付き選択肢とテキスト変化(再訪時に台詞が変わる等)
- §6 フォーク公開と作者への還流

つまり**現在の計画に従う限り、わくわくの源泉になりうる項目へ着手する枠が
構造上存在しない**。「P3.5まで完了したのに高揚感が無い」のは、完了したのが
永続化(P3.5)という土台工事であり、次も土台(P4/P5)が続く見通しだから、
という説明がつく。

また、「わくわくしない」の原因は複数の仮説に分解できる(→論点Q2):

| 仮説 | 内容 | 効く打ち手の例 |
|---|---|---|
| (a) コンテンツ不足 | 遊べるシナリオが実質「単純討伐」1本で、2周目以降の発見が無い | シナリオを2〜3本作る(実装ではなく創作) |
| (b) メカニクスの浅さ | タグ・条件分岐・報酬定義が無く、カード選択に戦略や蓄積の実感が薄い | §4/§5あたりの最小実装 |
| (c) 演出の薄さ | Web UIは機能的だが、めくる・出す・進む楽しさの演出が無い | UI/演出のサイクル |
| (d) 共有相手の不在 | 1人で作り1人で遊んでいる。感想も対戦相手も無い | 人に遊んでもらう(P4を待たずローカル/静的配布でも可能) |

どれが主因かで次の一手が大きく変わるため、実装より先に切り分けたい。

### 2. 進捗管理: 「完了の記録」は機能しているが「これからの管理」が無い

うまく機能している部分(維持する):

- サイクル粒度の進捗の正 = task.md frontmatter、roadmap = 索引、という
  正の一元化。食い違い時の優先順位も明文
- 1サイクル=1PR、ふりかえり→スキル/運用への反映ループ、決定ログ、design-sync

欠けている部分:

1. **状態語彙に「凍結」が無い。** `status` は `done | in-progress | planned`
   の3値([tasks/README.md](../README.md))。P4/P5を塩漬けにしても
   `planned` のまま残り、「次はP4」という含意が消えない。
2. **「次にやると決めたこと」と「いつかやりたいこと」の区別が無い。**
   roadmap はフェーズの静的な一覧で、Now/Next/Later にあたる軸が無い。
   RDRAの requirements も `status: realized | future` の2値で、
   ビューは「実現済みが積もる+将来が並ぶ」以上の情報を持たない。
   ご指摘の「完了が上に積もって見える」問題の直接の原因。
3. **「今後やりたいこと」の受け皿が実質無い。**
   future-requirements.md は「設計判断時に壊さないための意識リスト」で
   あって(冒頭で自ら宣言)、価値や優先度を議論・順位付けする場ではない。
   バックログに相当する文書が存在しない。
4. **RDRAデータの棚卸しがふりかえり手順に入っておらず、既に陳腐化している。**
   本見直しの調査中に発見: [rdra/requirements.yaml](../../rdra/requirements.yaml)
   の `pause-and-resume` と `take-rewards-home` は **P3.5で実装完了したのに
   `status: future`(「採用予定(phase3.5)」)のまま**。
   rdra/README.md は「規範文書の該当節を変えたら同PRで直す」と定めるが、
   フェーズ完了ふりかえりのチェックには含まれておらず、すり抜けた。
   (これは論点の決定を待たず修正してよい既知の乖離)

### 3. まとめ

進捗管理は「過去(何が終わったか)」の正確さに投資してきて、そこは機能して
いる。欠けているのは「未来(何を・なぜ・どの順でやるか)」を持つ場所と語彙。
そして計画の中身自体が土台工事に偏っており、価値(わくわく)の検証・増強を
行う工程が無い。塩漬けはその歪みを直す好機と捉える。

## 今後の方針の案

### 案A: 進捗管理の語彙と棚卸しを直す(小・即効。推奨: 先行実施)

1. `status` 語彙に `frozen`(凍結)を追加し、P4/P5 に適用。
   roadmap.md の状態列にも「凍結(再開条件: …)」と明記
2. 「これからやること」の置き場を作る(形態は論点Q3):
   Now(今やる)/ Next(次にやると決めた)/ Later(いつか)の3層で、
   フェーズ・future-requirements の各項目・単発改善を横断して並べる
3. rdra/requirements.yaml の棚卸し(P3.5実装分を `realized` へ)+
   agent-operations.md「フェーズ完了時のふりかえり」手順に
   「rdra/*.yaml の棚卸し」を1項目追加
4. (任意・論点Q5)docs-site の進捗/RDRAビューに凍結・Now/Next を反映

反映先: docs/tasks/README.md、roadmap.md、agent-operations.md、
docs/rdra/requirements.yaml、(Q3の結論次第で新文書)

### 案B: 価値検証の小フェーズを挿す(中。Q2の答えを見て要否・中身を決める)

P4の前に「わくわくの源泉探し」を目的とする短い探索フェーズ(仮: 体験検証)
を置く。従来フェーズとの違いは、完了条件を「機能が動く」ではなく
**「検証で学びを得た」**に置くこと。候補(Q2の主因仮説に対応):

- (a)なら: シナリオを2〜3本作る(コード変更ほぼ無し。創作タスク)
- (b)なら: §4タグ or §5条件テキストの最小実装+それを活かすシナリオ1本
- (c)なら: Web版の演出強化サイクル

  誰かに遊んでもらい、感想を得る(P4不要。P3成果物の範囲で可能)

### 案C: フェーズ駆動をやめてバックログ駆動に全面移行(大。当面見送り)

Now/Next/Later のバックログを進捗の正にし、フェーズ制を廃止する。
phase-cycle スキル・agent-operations.md・docs-site すべてに波及する大手術で、
塩漬けの今この瞬間にやる必然性は薄い。案Aで不足を感じたら再検討。

**推奨の組み合わせ: A を先に実施 → Q2 を議論して B の要否と中身を決定。
C は見送り。**

## 論点(1論点ずつ進める)

### Q1: P4/P5 の凍結範囲と再開条件

- **論点**: 塩漬けの対象は P4/P5 の両方か。再開条件(または見直し時期)を
  決めて書き残すか。
- **選択肢**:
  1. 両方凍結。再開条件を明記する(例: 「非同期で遊びたい相手が具体的に
     現れたら」「体験検証で continue の判断が出たら」)
  2. 両方凍結。再開条件は決めず「見直し日」だけ置く
  3. P5のみ凍結(P4は生かす)
- **決定**(2026-08-02): **P4/P5の両方を凍結**。再開は次の2条件を
  **両方**満たしたとき:
  1. 非同期で遊びたい相手が具体的に現れる
  2. DBスキーマ(PostgreSQLのデータ構造)を確定できるほど要件が安定する
  - 理由: 現状ではPostgresのデータ構造を決めること自体が時期尚早という感触
    (要件がまだ動く見込み。体験検証の結果次第でスキーマの前提が変わりうる)
- **反映先**: roadmap.md 状態列+凍結節、phase4/phase5 の task.md frontmatter、
  docs/tasks/README.md(`frozen` 語彙定義)— いずれも反映済み(2026-08-02)。
- **切り出し(別タスク)**: tools/docs-site の `frozen` 対応(progress.ts の
  型と STATUSES、ProgressView.tsx の STATUS_LABEL、styles.css のバッジ配色
  ライト/ダーク)は、議論を優先するため本ログから切り出した。変更内容は
  ブランチ `docs-site-frozen-status` に退避済み(2026-08-02)。
  **注意: このブランチを取り込むまで、frontmatter の `frozen` を含む本反映を
  master に入れると docs-site のビルド(Pages デプロイ)が落ちる。**
  マージ順は docs-site 側が先、または同時。

### Q2: 「わくわくしない」の主因はどれか

- **論点**: 現状分析1の仮説 (a)コンテンツ不足 / (b)メカニクスの浅さ /
  (c)演出の薄さ / (d)共有相手の不在 のうち、主因はどれか。
  これは実装で答えが出る問いではなく、プレイした本人の実感が一次情報。
- **選択肢**: (a)〜(d) の単独または組み合わせ(順位付け)
- **決定**(2026-08-02): 主因は **(c) 演出の薄さ**。Web化したときの貧弱さが
  目立っている(UIがカードになっていない/依頼を張り紙カードから選ぶような
  形にしたい/スマホで選択するには小さい)。あわせて方向性も決定:
  - **CardWirthとの差別化は「文章メイン」**。イラスト量では張り合わない
  - ただしカードの視覚的効果としてイラストは有効なので、**カードの種類に
    応じた既定アイコン**を用意する方式にする(1枚ずつ描かない)
  - カードは2サイズ: **小**(タイトル+アイコン。CardWirthにならい
    74x94の画像が収まるもの)と、**大**(スマホでも読みやすいもの)
  - カードの形は**白銀比(1:√2)の縦長**を想定
- **反映先**: 案B(体験検証・演出強化)のタスク起草時に、上記の方向性を
  設計文書(ui-visual-design.md 等)へ規範として起こす。本ログの記述は
  議論の経緯であり仕様の正ではない。起草は全論点の議論完了後(Q3〜Q5の
  結論とあわせてタスク化する)

### Q3: 「これからやること」の管理形態

- **論点**: Now/Next/Later をどこで管理するか。
- **選択肢**:
  1. roadmap.md に「今・次・いつか」節を追加(文書を増やさない。
     roadmapが「フェーズ索引」から「計画の入口」へ役割拡大)
  2. docs/backlog.md を新設(roadmapはフェーズ索引のまま。
     future-requirements.md は「設計影響メモ」として現状維持し、
     優先度はbacklog側で持つ)
  3. rdra/requirements.yaml の status 語彙を拡張(realized / now / next /
     later / frozen)し、RDRAビューをそのまま管理画面にする
- **決定**(2026-08-02): **選択肢1(roadmap.md に「今・次・いつか」節を
  追加)**。roadmap が「フェーズ索引」から「計画の入口」へ役割を広げる。
  優先度の正は roadmap のこの節に置き、RDRA側は従来どおり非規範の索引
  (ビューへの反映は Q5 で扱う)。初期の内容(案):
  - Now: 本見直しの反映一式(RDRA棚卸し・docs-site frozen対応
    =`docs-site-frozen-status` ブランチの取り込み)
  - Next: Q2で決めたカードUI・演出強化タスク
  - Later: future-requirements.md の各項目、P4/P5(凍結)
- **反映先**: 選択肢による(roadmap.md / 新文書+docs/README.md /
  rdra/README.md+requirements.yaml)。いずれでも「正を二重化しない」を守る
  (優先度の正は1箇所)
- **補足**: 3は見た目に最も効くが、YAML手編集が管理のボトルネックになる
  懸念あり。1か2で正を作り、3(ビュー反映)はQ5で扱うのが筋が良い。
