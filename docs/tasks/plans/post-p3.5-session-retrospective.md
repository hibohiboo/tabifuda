## 4. 課題・手戻り — 画面レビューで3周の修正が起きた件

docs-site D4〜D5の画面(screens.yaml)レビューで3回の修正が発生した:

1. シナリオ終了後に「もう一度遊ぶボタン」を根拠なく追加(実装にも
   future-requirements.mdにも記述が無い憶測)
2. 依頼選択のactorsを`[player, gm]`としたが、StartSessionは呼んだ本人が
   Gmとして登録される仕様で、usecases.yamlのstart-sessionも
   actors:[gm]のみ
3. GMのシナリオ在庫・カスタマイズ・募集というフロー全体が画面一覧から
   欠落

**根本原因は2種類あり、対処も異なる**:

- **1・2件目(自己チェックの不足)**: usecases.yaml・apps/webの実装という
  「既に決まっている情報」と照合すれば、エージェント単独で防げたミス。
  ユーザーの確認を待つ話ではなく、単純に裏取りが甘かった
- **3件目(確認タイミングの遅さ)**: 5画面という初期リスト自体が、
  根拠なく直感で挙げたもの。本来は「これは仮リストです、抜けがないか」を
  リストだけの段階(荒い段階)で確認すべきだったが、実際には説明文・
  アクター・usecasesまで**全部書き終えた後**のレビューになっていた。
  枠組み(画面のリストそのもの)ではなく中身(書いた内容の妥当性)への
  確認になっており、枠組みが違っていれば中身をどれだけ精査しても
  漏れは見つかりにくい

ユーザー所感: 「決まっていないことに対して確認をとっていないことに
原因がある。任せすぎて、チェック工程がうまく機能していなかった」。
実質、確認のタイミングが1回(しかも作り込んだ後という遅いタイミング)に
集約されてしまっていた。

**次からの具体行動として合意**: 未確定なものを作るときは、作り込む前の
一番荒い段階(名前の列挙だけ等)で一度立ち止まって確認を挟む。
作り込んでからのレビューは「中身の妥当性」しか検証できず、
「枠組みの過不足」は検証しにくいため、確認のタイミングを分離する。

## 5. 進め方について — 双方の指示の出し方

**ユーザー側の所感**: 「画面ビューをいきなり頼んだこと」。誰がどう使うのか
(アクター)・何をしたいのか(要求)が先に無いと、画面の作りようがなかった。
D4の依頼(タスク2「docs-site改修」の一部として画面ビューを起票した)
自体が、本来その手前にあるべき要求・業務フローの整理より先に出ていた。

**エージェント側の所感**: D3〜D5の実装作業には、Q1〜Q6の議論で機能した
「型」(1論点ずつ・決定ログで区切る)に相当する構造が最初から無かった。
Q1〜Q6はほぼ手戻りが起きなかったのに対し、D3〜D5(特に画面まわり)は
3周の手戻りが起きており、この対比がそのまま「型の有無」の差だったと見ている。

**両者に共通する構図**: 指示する側(ユーザー)も実行する側(エージェント)も、
「このレイヤーの手前に、まだ整備されていないレイヤーがある」ことに
仕事に着手する前に気づけなかった。ユーザーは依頼を出す時点で、エージェントは
依頼を受けて作業する時点で、それぞれ同じ見落としを素通りしており、
どちらか一方が気づいて止める機会が無いまま、ワイヤーフレームという
作り込んだ段階まで進んでしまった。
