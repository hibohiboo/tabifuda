# P6 C1由来のハーネス改良(スキル/CLAUDE.mdの変更範囲分岐)

正の反映先はCLAUDE.md・`.claude/skills/phase-cycle/SKILL.md`・
`.claude/skills/client-conventions/SKILL.md`・
`docs/design/client-conventions.md`・`docs/agent-operations.md`。
本文書はP6サイクルの過程でこの改良が生まれた経緯メモ(実装は別ブランチ)。

## 経緯

C1完了報告時、ユーザーから2点の指摘があった:

1. `crates/`に変更が無いのに`cargo fmt --check`を無条件実行していた
   (儀式的で意味がない)
2. `tools/docs-site`に`lint`スクリプトが無いのに
   `pnpm --filter docs-site lint`を実行しエラーになった
   (package.jsonのscriptsを事前確認していなかった)

「まっすぐやりたいことをやるために、スキルやエージェントを活用できないか」
という問いを受けて検討した。

## 検討1: エージェント活用は見送り

ADR 0004「人間の判断を要する作業はエージェント化しない」の原則自体には
抵触しない(検証コマンドの選択は機械的判断)が、以下の理由でエージェント化は
見送った:

- 検証自体は数秒〜数十秒のコマンド数個で完結する軽量作業であり、
  サブエージェント起動のコールドスタート・コンテキスト受け渡しコストの方が
  高くつく
- 根本原因は「変更範囲に応じた実行判断ロジックがどこにも書かれていないこと」
  であり、エージェントに投げても同じ場当たり判断を繰り返すだけで解決しない

→ スキル文書・CLAUDE.mdに判断ルールを明記する方針とした。

## 検討2: phase-cycleスキルを分割するか(★本題)

ここでユーザーから「コアとフロントエンドは触るときに考慮すべきことが違う」
との指摘があり、**phase-cycleスキル自体をコア向け/フロントエンド向けに
完全分割するか**を検討した。

現状の内訳を洗い出した結果:

| 箇所 | 内容 | 属性 |
|---|---|---|
| 0.6 型骨格タスクの型棚卸し | 「参照はあるが定義が無い」型の洗い出し | コア特有(Rust型骨格) |
| 1. Event/Command/PatchOp追加は要相談 | — | コア特有 |
| 2. コアの純粋性・decide/apply・受理/拒否対テスト | — | コア特有 |
| 4.1 cargo test/clippy/fmt | 変更範囲を無視して無条件実行していた | コア特有(今回の問題箇所) |
| 4.2 bindings再生成 | crates変更時のみの条件付き(既に対応済み) | コア→TS波及 |
| 0/1/3/4の残り(ブランチ運用・チェックリスト化・design-sync・ふりかえり等) | — | **完全に共通** |

フロントエンド特有の考慮(CSSの型解決・クラス名衝突回避・
コンポーネントカタログへの追加手順等)は、当時スキルにも設計文書にも
ほぼ書かれていなかった。`core-invariants`スキルが先に整備され、対になる
フロントエンド版が無かったための偏りと判断した。

### 選択肢

- **a) 完全分割**: `phase-cycle-core` / `phase-cycle-frontend` の2スキルに分ける
- **b) 1スキルのまま**: 骨格は維持し、手順内(「2.実装」「4.終わり方」等)に
  「コアに触れる場合/フロントエンドに触れる場合」の分岐ブロックを追加。
  フロントエンド側の詳細規約は`client-conventions.md`への参照を
  `core-invariants`と対になる形へ格上げする

### 結論: b) を採用(スキルは分割しない)

理由:

1. ブランチ運用・チェックリスト化・design-sync・frontmatter更新・
   ふりかえり等の骨格(0/1/3/4の大半)はコア/フロントエンド問わず
   完全に共通しており、完全分割すると変更のたびに2箇所を同期する
   メンテナンスコストが生じる
2. 1サイクルでコアとTS両方に触れるケース(例: P3のようなbindings連動
   サイクル)で「どちらのスキルを呼ぶか」という余計な判断が新たに
   生まれてしまう
3. 既存の`core-invariants`スキル(phase-cycleから参照される薄い索引
   スキルで、正はdocs/design/test-strategy.md)と同型のパターンとして
   `client-conventions`スキルを新設すれば、骨格を割らずに参照先だけを
   分けられる(既存の設計哲学の横展開)

## 実施内容(別ブランチ`harness-frontend-conventions`、コミット`b3f9094`)

このハーネス改良自体は「ソースコード変更はタスク発行が前提」の原則
(agent-operations.md)と同じ理由で、P6 C1の実装(`phase6`ブランチ)とは
別ブランチで行った。関心事(カードUI実装 vs ハーネス改良)を分けるため。

- CLAUDE.md: 「必読文書」表・「コマンド」節・「作業の終わり方」に
  TS側(pnpm系)の扱いを追記(P3以降の追記漏れを解消)
- phase-cycleスキル: 「開始の儀式」「実装」「終わり方」を
  crates/変更時・TS側変更時で分岐する形に書き換え。pnpm系は
  `--if-present`を使い、package.json事前確認を不要にする
- `client-conventions`スキルを新設(`core-invariants`のTS版)
- `docs/design/client-conventions.md`にCSS副作用importの型解決・
  クラス名衝突回避の実装知見を追記
- `docs/agent-operations.md`のスキル一覧・`docs/agent-journal.md`
  (2026-08-12エントリ)に経緯を記録

## 影響

次サイクル(C2)以降は改良後のphase-cycleスキルに従う。`harness-frontend-
conventions`ブランチのmasterへの統合は、`phase6`ブランチとは独立に
人間の判断を仰ぐ。
